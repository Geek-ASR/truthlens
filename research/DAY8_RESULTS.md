# Day 8: Frozen Final Experiment Run — Results

Frozen at git tag `truthlens-day8-frozen`. Dataset: 9 real Tier-1 items
(`research/dataset/items.jsonl`). All tables below are generated by
`backend/research/day8_final_tables.py` from real result files in
`research/results/` — nothing here is hand-typed or estimated.

## Headline finding, reported first because it's the least flattering one

**On the paired 6-item comparison (the only fair one — see below), Full
TruthLens (33.3%, 2/6) does not beat either single-shot search baseline:
Baseline 2 (Search+LLM) scores 66.7% (4/6) and Baseline 3
(Search+RAG+LLM) scores 50.0% (3/6) on the same items.** This is the
real result of this experiment. It is reported first and prominently
because Rule ("if a baseline beats TruthLens on some metric: REPORT IT")
requires exactly that, not because it's the most flattering framing
available.

**This is not a mysterious overall weakness — it traces directly to
specific component failures already diagnosed on Days 4-6**, which is
itself the more useful finding than the raw accuracy gap alone:

- **item-0006 and item-0007**: Full TruthLens outputs `UNVERIFIED` on
  both — not because it researched them and found insufficient evidence,
  but because **claim extraction found zero verifiable claims** for
  either (`MULTIMODAL_EVALUATION.md`, Day 4 — item-0006's Whisper
  transcript is badly garbled nonsense; item-0007's is degraded and
  repetitive). Baseline 2, given only a raw claim string and search
  snippets with no claim-extraction stage to fail, happened to guess
  `MOSTLY_FALSE` for both — matching the ground-truth bucket by a
  simpler, less decomposable process. TruthLens's deeper architecture
  had no claim to work with at all; the single-shot baseline never
  needed one.
- **item-0004 and item-0005**: both systems get these wrong, but for
  different, already-documented reasons — TruthLens's wrong verdicts
  here are the exact two cases `VALIDATOR_EVALUATION.md` (Day 5) already
  identified as validator false negatives (confident labels contradicted
  by real Tier-1 ground truth, undetected by the citation/number
  -grounding checks).
- **item-0001 and item-0002**: both systems get these right.

**McNemar analysis** (paired, n=6, Baseline 2 vs. Full TruthLens):
both-correct=2, both-wrong=2, Baseline-2-only-correct=2,
TruthLens-only-correct=0. Exact McNemar p=0.5 (2 discordant pairs,
maximally underpowered — reported for completeness, not as evidence of
anything). **This is not a claim that TruthLens's architecture is
worse than a single-shot baseline in general** — it is a claim that on
this specific, tiny, real sample, the components most responsible for
supposed architectural advantage (claim decomposition, deterministic
validation) each had a real, already-diagnosed failure that happened to
cost more than they gained. Table 3 below shows decomposition *did*
help once claim extraction actually produced multiple claims to
aggregate — the deficit here is claim-extraction *coverage* on hard
audio, not the decomposition/aggregation mechanism itself.

| Config | n | Correct | Accuracy | 95% CI |
|---|---|---|---|---|
| Baseline 1 (LLM-only) | 9 | 2 | 22.2% | [6.3%, 54.7%] |

**Baselines 1-3 ran on all 9 items (Ollama-only, no Gemini dependency,
so unaffected by the quota gap below). Full TruthLens's real number
covers only 6 — this row is not directly comparable to the others
without restricting to the same 6 items, which Table 2 does.** Reported
side by side here anyway, with this caveat attached, rather than
omitted, since it's still real data.

## Table 2: Paired comparison, same 6 items for every configuration

| Config | n | Correct | Accuracy | 95% CI |
|---|---|---|---|---|
| Baseline 1 (LLM-only) | 6 | 0 | 0.0% | [0.0%, 39.0%] |
| Baseline 2 (Search+LLM) | 6 | 4 | 66.7% | [30.0%, 90.3%] |

kind of restriction.

**This is a real, positive result for RQ2's decomposition-specific
question**: on item-0001, the single highest-importance claim happened
to land on `UNVERIFIED` (missing-citation no-op downgrade — see
`VALIDATOR_EVALUATION.md`), but aggregating all 4 extracted claims via
the real, deterministic `derive_overall_verdict()` correctly recovered
`MOSTLY_FALSE`. n=4 is far too small to generalize, but this is the one
component-level ablation in this program where TruthLens's specific
architectural mechanism demonstrably helped rather than hurt, and it is
reported with the same prominence as the headline negative finding
above, not buried beneath it.

## Real gap found and fixed during this exact run

Extending the real pipeline run to items 0008/0009 hit a genuine
`MissingGreenlet` crash — the same bug class already fixed once in
production code (`app/api/routers/reels.py`'s `quick_fact_check`): after
a per-claim exception handler called `db.rollback()`, the next line's
synchronous `claim.text` access on an already-loaded-but-now-expired ORM
object crashed the whole script instead of just recording that one
claim's failure. Fixed in `backend/research/validator/run_validator_audit.py`
by capturing `claim.id`/`claim.text` before the try block, matching the
production fix's pattern. Re-verified live: the script completed
without crashing on the second attempt (though it then hit the real
Gemini quota exhaustion below, a separate, genuine external constraint).

## Known, disclosed gaps in this Day 8 pass

- **item-0003**: never successfully ingested (persistent Instagram
  "empty media response," confirmed across 3 independent attempts this
  program — Day 4 and Day 8). Excluded from every table above, not
  scored as a failure.
- **items 0008/0009, full-TruthLens condition**: blocked by real
  Gemini free-tier quota exhaustion (confirmed live: two consecutive 429
  errors, one from an evidence-analysis escalation, one from
  claim-extraction's own escalation) during this exact Day 8 run.
  Baselines 1-3 completed for both items (no Gemini dependency by
  design — see `BASELINE_SPEC.md`). This is a real, external,
  time-of-day resource constraint, not a system defect, and not
  something forced past by retrying indefinitely within this pass.
- Evidence/validator/claim-coverage metrics from Days 5-6 are not
  re-computed for items 0008/0009 for the same reason.
- Per-class F1, Macro-F1, and full precision/recall breakdowns are not
  computed in this pass — at n=6-9 with several label classes appearing
  0-1 times, per-class F1 would mostly be undefined or based on a single
  observation; reported here as a scope decision rather than presented
  with misleadingly precise-looking zeros and ones.

## What would change these numbers

Everything in this document should be treated as a snapshot of a
specific, small, real run, not a settled measurement — re-running Table
1/2 once Gemini quota resets (to complete items 0008/0009) and once the
dataset grows further are both concrete, named next steps, not vague
